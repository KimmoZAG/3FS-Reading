第 01 章 · 约 5 分钟

认识 3FS

想象训练集增大以后，几百个计算节点都要从同一组文件随机取样。共享存储既要跟得上并发读取，也要让应用继续使用熟悉的文件接口。

3FS 服务哪些工作负载？

3FS 全称 Fire-Flyer File System，是 DeepSeek 开源的高性能分布式文件系统。计算节点可以通过同一文件命名空间访问远端数据。存储节点上的 SSD 分担 I/O，RDMA 网络负责高速数据传输。

训练数据读取
多个数据加载器并发读取样本。小随机读要同时看 IOPS 和尾延迟，大块顺序读则更容易跑满带宽。
训练检查点
各 worker 集中写出模型和优化器状态。关注并行写入的总带宽，以及检查点什么时候可安全使用。
推理 KVCache
重复请求可复用已有缓存。SSD 扩大容量，同时需要关注缓存命中率和取回缓存的延迟。

先分清三个指标

吞吐量衡量单位时间传输的字节数，IOPS衡量单位时间完成的操作次数，延迟衡量一笔 I/O 等了多久。上游公布的约 6.6 TiB/s 是 180 台存储节点在大块读压测中的集群聚合吞吐，解释结果时还要一起看请求大小、并发和硬件条件。

官方 README 的性能测试

自测 · 训练节点读小样本时，应该额外看什么？

看小块随机读的 IOPS、P95/P99 延迟，以及数据加载器能否及时把样本交给 GPU。用同样的块大小和并发度比较结果。

下一章 · 系统架构

第 02 章 · 约 7 分钟

系统架构

元数据回答文件是谁、如何定位。Storage 回答字节在哪里、哪个版本可读。Mgmtd 让客户端和服务共享集群路由。

四个组件如何协作

Client
应用通过 FUSE 挂载使用文件接口。客户端取得文件布局，结合路由信息算出要访问的存储链。
Meta
处理路径查找、属性、权限和目录操作。目录项和 inode 持久化在 FoundationDB，Meta 实例按无状态方式设计。
Storage
管理本地 SSD 上的存储目标（target），提供 chunk 读取、写入和复制。一个 SSD 可以承载多个 target。
Mgmtd
收集服务心跳，维护成员和链配置，向服务及客户端提供路由。集群由主 Mgmtd 负责更新链。

跟踪一次文件读取

  1. 定位文件。需要查找路径或刷新属性时，客户端向 Meta 请求 inode 和布局。FUSE 的查找和打开路径可以复用客户端缓存。
  2. 计算数据路由。客户端将读取范围按 chunk 边界拆开，结合布局和 Mgmtd 下发的路由选出要访问的链。
  3. 读取数据。常见路径由客户端直接请求 Storage。存储服务从本地 SSD 读取数据，通过网络传给客户端。
USRBIO 如何接入？

应用仍用文件接口打开文件，再注册 fd。随后通过共享内存的 Iov 存放数据，通过 Ior 提交异步 I/O 并收取完成结果。元数据操作沿用原来的文件接口。

官方架构说明USRBIO API 参考

自测 · Meta 服务重启后，目录项从哪里读回？

目录项和 inode 的持久化记录在 FoundationDB。客户端可在有可用实例时切换 Meta 服务。

下一章 · 文件与数据布局

第 03 章 · 约 8 分钟

文件与数据布局

有了文件标识和读取偏移，客户端就能计算目标 chunk 与副本链。先做一遍手算，再去核对源码。

从文件名到 chunk

路径查找沿目录项进行。目录项通过父目录 inode 与名字找到子对象，inode 保存权限、时间戳等属性。文件 inode 还保存长度和数据布局，包括 chunk 大小、条带宽度及选中的链信息。

以普通文件数据为例，chunkIndex 由偏移整除 chunk 大小得到，块内偏移取余。chunk ID 包含 inode ID 和 chunk 序号。条带宽度表示这个文件使用的链数，文件布局的链列表决定每个条带槽对应哪条链。

chunkIndex = floor(offset / chunkSize)
chunkOffset = offset % chunkSize
stripeSlot = chunkIndex % stripeSize
chain = layoutChains[stripeSlot]

试算 640 KiB 处的数据

取教学用布局，chunk 大小为 256 KiB，链列表为 [A, B, C]。640 KiB 落在从 0 开始计数的第 2 号 chunk，块内偏移为 128 KiB。第 2 号条带槽映射到 链 C，第 3 号 chunk 则回到链 A。

分条带与做副本

不同 chunk 分散到多条链，以并行使用不同存储资源。一个 chunk 内的多个副本位于同一条链的不同 target 上，以便在单个目标故障时保留可用数据。

下一章 · 读写与 CRAQ

第 04 章 · 约 10 分钟

读写与 CRAQ

同一个 chunk 写到链上的所有可写目标。读请求可以在可读副本之间分摊，遇到正在写入的副本时要检查本地版本。

一次写入如何沿链传播

  1. 从链头开始。客户端把写请求发给 Head，链头串行化同一 chunk 的写入。各目标检查请求携带的链版本。
  2. 逐跳写入待提交版本。Head 与中间目标暂存新版本，并向后继转发。Tail 收到写入后提交新版本。
  3. 确认逐跳返回。Tail 的确认向前传播。中间目标及 Head 各自提交对应版本，最终由 Head 确认写入。

3FS 怎样处理未提交读

稳定状态下，任一可读目标都能返回本地已提交数据。原始 CRAQ 论文中的强一致读在副本有未提交更新时会向链尾查询已提交的版本。3FS 在本地 commitVer 和 updateVer 不同时，默认返回 kChunkNotCommit，存储客户端将其归类为快速重试错误。显式允许未提交读时，客户端可以取得待提交版本。

中间目标离线时

Mgmtd 根据心跳更新目标状态与链版本，剩余健康目标可以组成新的有效链。请求若使用旧路由，可能收到版本不匹配错误，客户端需要刷新路由或重试。恢复的目标完成同步后再恢复相应的服务资格。

自测 · Tail 已提交 v2、Mid v2 仍待提交，默认读 Mid 会怎样？

Mid 的两个版本号不同，返回 kChunkNotCommit。推进提交确认后再读，Mid 就能从本地返回 v2。

第 05 章 · 约 12 分钟

从源码读起

沿普通 FUSE 读取的主路径追踪。从入口拿到的 off 和 size，正好对应之前做过的拆块练习。

一次读请求的四个检查点

  1. hf3fs_readsrc/fuse/FuseOps.cc

    从文件句柄拿 inode，准备缓冲区，调用 PioV::addRead 和 executeRead。

  2. PioVsrc/fuse/PioV.cc

    找出 chunk 边界和每段长度，用文件布局为每个 I/O 算出链，最后调用存储客户端的 batchRead。

  3. StorageClientImpl::batchReadsrc/client/storage/StorageClientImpl.cc

    跟进读请求的路由、批次执行和重试。搜索 isFastRetryError，查看哪些错误会触发快速重试。

  4. StorageOperator::batchReadsrc/storage/service/StorageOperator.cc

    跟到 Storage 侧读入口，再读 ChunkReplica::aioPrepareRead，查看数据和提交版本的检查时机。

另外两条路可以怎么追

找元数据时，从 FUSE 的 hf3fs_lookup 追到 metaClient->stat，从 src/meta/store/ 里的目录项和 inode 结构理解事务。找写入时，从 StorageOperator::write 追到更新、转发和提交，最后对照 specs/DataStorage 的 P 模型。

PioV 在客户端按 chunk 边界拆区间。ChunkReplica 在 Storage 侧检查本地副本版本。

练习题 · 读取一个跨块样本

文件采用 256 KiB chunk，链列表为 [A, B, C]。应用从 500 KiB 处读 40 KiB。此时链 C 的中间目标刚收到新版本，链尾尚未提交。

  1. 计算两段读取各自的 chunk 序号、块内偏移、长度与链。
  2. 如果链 C 的这段读被派给了中间目标，默认读会返回什么？
  3. 用两句话复述这一次读取中 Meta、Mgmtd 和 Storage 各自负责的事。

用条带实验核对偏移用复制实验核对状态

展开参考答案

第一段在 chunk 1、链 B，块内偏移 244 KiB，读 12 KiB。第二段在 chunk 2、链 C，块内偏移 0，读剩余 28 KiB。

若链 C 的中间目标本地有未提交更新，默认读返回 kChunkNotCommit，客户端可重试。Meta 提供文件布局，Mgmtd 提供链路由。客户端用这两份信息计算目标，由 Storage 读出字节。
